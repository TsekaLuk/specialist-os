# ADR-004 — Music Intelligence Pack

- **Status:** Accepted
- **Date:** 2026-09-07
- **Decision Type:** Capability Pack / Provider Selection
- **Applies To:** Specialist OS
- **Depends On:** Core 15 Capability Set
- **Scope:** Local-first music analysis, separation, symbolic transcription, fingerprinting, and optional music generation

## 1. Decision

Specialist OS will add a first-class **Music Intelligence Pack** without expanding the frozen Core 15 capability set.

The Music Pack is divided into three tiers:

1. **Stable Specialists** — production-oriented, local-first capabilities with mature developer ecosystems.
2. **Experimental Specialists** — capabilities with clear value and useful local implementations, but insufficient production consensus to be treated as stable defaults.
3. **Heavy Generative** — optional generative models that are useful but do not share the same semantics as measurement/extraction specialists.

Accepted capability/provider mapping:

| Capability | Default Provider | Tier | Decision |
|---|---|---|---|
| `music.analyze` | Essentia | Stable | Accept |
| `music.separate` | audio-separator | Stable | Accept |
| `music.fingerprint` | Chromaprint | Stable | Accept |
| `music.transcribe_notes` | Basic Pitch | Stable | Accept |
| `music.transcribe_vocal` | ROSVOT | Experimental | Accept, optional install |
| `music.transcribe_multitrack` | MuScriptor | Experimental | Accept |
| `music.generate` | ACE-Step 1.5 | Heavy Generative | Accept, optional install |
| VocalParse | — | Watchlist | Do not integrate yet |
| YourMT3+ | — | Watchlist | Do not integrate yet |

The public abstraction is capability-first. LLMs and applications should not need to know provider names.

---

## 2. Context

Specialist OS currently provides general perception, document, speech, identity, geometry, and media utilities. Music is a strong candidate for the first domain pack because it already has multiple mature specialist tools that produce measurable and structured outputs locally.

Music tasks that should not be delegated to a general LLM/VLM include:

- exact BPM and beat extraction;
- key / scale / tonal analysis;
- source separation;
- audio-to-MIDI transcription;
- multi-instrument symbolic transcription;
- singing-note transcription;
- audio fingerprinting and duplicate detection.

These tasks have stable semantics and can be expressed as reusable machine capabilities.

Music generation is intentionally treated separately because it produces a creative artifact rather than a measurement or extraction result.

---

## 3. Capability Taxonomy

The Music Pack exposes the following namespace:

```text
music.analyze
music.separate
music.fingerprint

music.transcribe_notes
music.transcribe_vocal
music.transcribe_multitrack

music.generate
```

The following semantic distinctions are mandatory:

- **Stem**: an audio waveform representing an isolated source, e.g. `vocals.wav`.
- **Note**: a symbolic musical event with pitch, onset, offset, and optional velocity.
- **Track**: a group of symbolic note events assigned to an instrument or role.
- **Score**: quantized and notated musical structure suitable for MIDI / MusicXML / sheet representation.
- **Fingerprint**: a compact representation for identifying near-identical recordings; not a semantic embedding.

## 4. Stable Capability — `music.analyze`

### Provider

**Essentia**

### Semantics

`music.analyze` extracts deterministic or model-assisted music information retrieval features from audio.

Initial supported features:

```text
duration
tempo / BPM
beat positions
onsets
key
scale
tuning
loudness
chroma
MFCC
selected spectral descriptors
```

### API

```python
music.analyze(
    audio,
    features=None,
)
```

If `features=None`, the runtime returns a compact recommended feature set rather than every Essentia descriptor.

### Example result

```json
{
  "bpm": 123.8,
  "key": "F#",
  "scale": "minor",
  "beats": [0.48, 0.97, 1.45],
  "loudness_lufs": -9.8
}
```

### Requirements

- Numeric results must be generated by the specialist, not inferred by the LLM.
- High-volume arrays such as beat tracks may be returned as artifacts when appropriate.
- The API must remain independent of Essentia-specific class names.

---

## 5. Stable Capability — `music.separate`

### Provider

**audio-separator**

### Decision rationale

Specialist OS intentionally integrates the runtime rather than binding the capability to a permanent Demucs / MDX / RoFormer checkpoint.

Source separation models change quickly. The stable abstraction is:

```text
music.separate()
```

not:

```text
run_bs_roformer_xxx()
```

### API

```python
music.separate(
    audio,
    stems=["vocals", "instrumental"],
    profile="balanced",
)
```

Potential stem vocabulary includes:

```text
vocals
instrumental
drums
bass
guitar
piano
other
```

The provider/model registry determines which combinations are actually supported.

### Profiles

- `fast`: lightweight local separator.
- `balanced`: current recommended model / configuration.
- `quality`: quality-oriented model or ensemble where hardware allows.

### Result

```json
{
  "stems": {
    "vocals": "artifact://vocals",
    "instrumental": "artifact://instrumental"
  }
}
```

Waveforms must never be embedded directly into JSON responses.

---

## 6. Stable Capability — `music.fingerprint`

### Provider

**Chromaprint**

### Semantics

This capability answers whether audio is likely to represent the same underlying recording or a near-equivalent encoding.

It is not a style similarity or semantic retrieval API.

### API

```python
music.fingerprint(audio)
music.compare_recording(audio_a, audio_b)
```

### Result

```json
{
  "duration": 213.4,
  "fingerprint": "..."
}
```

A future online enrichment provider may resolve fingerprints through AcoustID / MusicBrainz, but network lookup is not required for the local core capability.

---

## 7. Stable Capability — `music.transcribe_notes`

### Provider

**Spotify Basic Pitch**

### Semantics

```text
audio -> note events -> MIDI
```

This capability is optimized for single instruments and comparatively simple polyphonic audio. It must not claim to provide reliable instrument-attributed full-song multitrack transcription.

### API

```python
music.transcribe_notes(audio)
```

### Result

```json
{
  "notes": [
    {
      "pitch": 60,
      "start": 0.13,
      "end": 0.72,
      "velocity": 0.81
    }
  ],
  "midi": "artifact://midi"
}
```

---

## 8. Experimental Capability — `music.transcribe_multitrack`

### Provider

**MuScriptor**

### Status

Experimental — accepted.

### Semantics

```text
full music mix
-> instrument-attributed symbolic note events
-> multi-track MIDI / score artifacts
```

This fills a capability that Basic Pitch does not cover.

### API

```python
music.transcribe_multitrack(
    audio,
    profile="balanced",
)
```

### Normalized result

```json
{
  "tracks": [
    {
      "instrument": "electric_guitar",
      "notes": [],
      "midi": "artifact://guitar-midi"
    },
    {
      "instrument": "bass",
      "notes": [],
      "midi": "artifact://bass-midi"
    }
  ],
  "midi": "artifact://full-midi",
  "musicxml": "artifact://score"
}
```

### Model profiles

Recommended mapping:

```text
fast     -> Small (~100M class)
balanced -> Medium (~300M class)
quality  -> Large (~1B+ class), only when hardware is suitable
```

The exact checkpoint mapping belongs in the provider registry and may change without changing the capability contract.

### Caveats

The runtime must surface warnings when transcription conditions are likely to produce poor notation, including unstable tempo / rubato and low-confidence instrument attribution.

Example:

```json
{
  "warnings": [
    {
      "code": "UNSTABLE_TEMPO_TRANSCRIPTION"
    }
  ]
}
```

### License metadata

MuScriptor model weights must be marked as non-commercial where applicable. This is acceptable for the current self-use deployment but must be preserved in registry metadata.

---

## 9. Experimental Capability — `music.transcribe_vocal`

### Provider

**ROSVOT**

### Status

Experimental / optional installation.

### Semantics

```text
singing voice
-> vocal note events / melody MIDI
```

This is distinct from speech ASR.

```text
speech.transcribe       -> words
music.transcribe_vocal  -> sung musical notes
```

### API

```python
music.transcribe_vocal(audio)
```

### Result

```json
{
  "notes": [
    {
      "pitch": 67,
      "start": 0.31,
      "end": 0.74
    }
  ],
  "midi": "artifact://vocal-midi"
}
```

### Packaging policy

ROSVOT must not be part of the default laptop Music Pack install until its portability and packaging quality improve.

It is installed through:

```bash
specialist install music-experimental
```

or:

```bash
specialist provider install rosvot
```

Provider failure must not affect stable Music Pack capabilities.

---

## 10. Watchlist — VocalParse

### Decision

Do not integrate yet.

### Reason

VocalParse is compelling because it attempts to jointly emit:

```text
lyrics
pitch
note values
tempo
```

However, its architecture is a specialized large audio-language model rather than a narrow specialist primitive. It is also too new to meet the project's production-consensus requirement.

The current preferred composition remains:

```text
Whisper
+
ROSVOT
+
Essentia
+
deterministic alignment
```

### Reconsider when

- external developer adoption becomes meaningful;
- singing lyric accuracy is proven materially better than existing ASR pipelines;
- structured output reliability improves;
- local inference becomes operationally attractive;
- it provides a clear system-level advantage over composed specialists.

---

## 11. Watchlist — YourMT3+

### Decision

Do not integrate as a direct provider at this stage.

### Reason

Its primary capability overlaps with:

```text
music.transcribe_multitrack
```

which is already represented by MuScriptor.

Maintaining two experimental AMT stacks on day one would approximately double dependency, model, test, and platform-maintenance burden without doubling product capability.

It may be reconsidered as a secondary provider if Specialist OS's own benchmarks show meaningful superiority for specific genres, instruments, or recording conditions.

---

## 12. Heavy Generative Capability — `music.generate`

### Provider

**ACE-Step 1.5**

### Tier

Heavy Generative / optional.

### Semantics

This capability creates new music. It is categorically different from measurement, extraction, or symbolic transcription.

### API

```python
music.generate(
    prompt,
    lyrics=None,
    duration=None,
    bpm=None,
    key=None,
    reference_audio=None,
)
```

### Result

```json
{
  "audio": "artifact://generated-song",
  "duration": 184.2,
  "provider": "ace_step"
}
```

### Installation

It must not be installed by the default Music Pack.

```bash
specialist install music-generation
```

### Boundary

Provider-specific generation controls belong in `provider_options`; they must not destabilize the generic `music.generate` contract.

## 13. Composite Capability — `music.parse_singing`

A composed singing parser may be exposed without adopting VocalParse as a monolithic backend.

Recommended graph:

```text
Singing Audio
    |
    +--> Whisper  ------> lyrics / word timestamps
    |
    +--> ROSVOT   ------> vocal note events
    |
    +--> Essentia ------> tempo / beats / tuning
                
        deterministic alignment
                |
                v
       structured singing result
```

This capability should remain composite and evidence-preserving.

---

## 14. Composite Capability — `music.transcribe_full`

A higher-level full transcription workflow may combine:

```text
Full Mix
   |
   +--> music.analyze
   |
   +--> music.transcribe_multitrack
   |
   +--> music.separate
             |
             +--> Basic Pitch / ROSVOT on selected stems
```

The first version does not require sophisticated automatic reconciliation between competing symbolic transcriptions.

## 16. Artifact Model

Add / standardize the following artifact semantics:

```text
music/midi
music/musicxml
music/score
music/fingerprint
music/analysis
```

Existing `audio/*` artifacts are reused for source audio, stems, denoised audio, and generated music.

Large MIDI / score / analysis payloads may be returned as artifact references rather than embedded directly into tool context.

```text
WATCHLIST

```

Current classification:

| Provider | Maturity |

## 18. Benchmark Strategy

Specialist OS must maintain its own real-world music fixture set instead of accepting paper benchmark claims as provider-selection truth.

Minimum fixture categories:

```text
solo_piano
solo_guitar
solo_bass
clean_vocal
vocal_with_backing
pop_full_mix
rock_full_mix
electronic
classical
jazz
rubato
low_quality_recording
```

### `music.analyze`

Track:

```text
BPM error
key accuracy
beat F-measure
latency
```

### `music.separate`

Track:

```text
SDR / applicable separation metric
stem bleed
artifacts
latency
memory
```

### `music.transcribe_notes`

Track:

```text
note onset F1
note-with-offset F1
pitch accuracy
```

### `music.transcribe_vocal`

Track:

```text
note F1
pitch accuracy
onset / offset accuracy
```

### `music.transcribe_multitrack`

Track:

```text
note F1
instrument attribution F1
track completeness
notation usability
latency
peak memory
```

Provider promotion must consider reliability, laptop performance, packaging quality, and real music results alongside accuracy.

## 19. Promotion Criteria

### MuScriptor -> STABLE

Requires:

- sustained Apple Silicon stability;
- acceptable performance across multiple genres;
- sufficiently reliable instrument attribution;
- no major dependency/install fragility;
- measurable value over simpler separation + per-stem Basic Pitch workflows.

### ROSVOT -> STABLE

Requires:

- mature packaging;
- portable inference beyond research-centric CUDA setups;
- stronger Apple Silicon / cross-platform support;
- broader real-world validation;
- evidence of meaningful external developer use.

## 20. LLM Tool Exposure

LLMs receive capability names, not provider names.

Recommended tool exposure:

```text
music_analyze
music_separate
music_fingerprint
music_transcribe_notes
music_transcribe_vocal
music_transcribe_multitrack
music_generate
```

Provider override is a developer/debug feature and should not normally be exposed to model tool selection.

Intent mapping examples:

```text
"这首歌多少 BPM、什么调？"
-> music.analyze

"把人声去掉"
-> music.separate

"把这段钢琴变成 MIDI"
-> music.transcribe_notes

"把这个人的演唱旋律扒出来"
-> music.transcribe_vocal

"把整首歌扒成多乐器 MIDI"
-> music.transcribe_multitrack

"这两个 MP3 是不是同一录音？"
-> music.fingerprint

"生成一首 120 BPM 的电子摇滚"
-> music.generate
```

## 21. Security and Safety Boundary

LLM-facing music tools must not expose arbitrary shell arguments to FFmpeg, model CLIs, or other native executables.

File and artifact access follows the existing Specialist OS artifact sandbox / explicit-input policy.

Voice and copyright-sensitive workflows are not given special persistence behavior by default. Generated or extracted artifacts follow existing retention policies.

## 23. Consequences

### Positive

- Music becomes the first domain pack demonstrating that Specialist OS can expand without inflating Core.
- The pack covers analysis, extraction, symbolic transcription, identity-like fingerprinting, and generation.
- Capability semantics remain stable while AMT and separator models continue to evolve.
- Laptop-first workflows remain useful without installing heavy generation models.
- Experimental models can be evaluated without being misrepresented as production consensus.

### Negative

- MuScriptor and ROSVOT increase maintenance burden for research-originated runtimes.
- Some capabilities will not have uniformly strong results across genres and recording conditions.
- Music generation requires significantly more storage and compute than stable analysis tools.
- Full score reconstruction remains an imperfect problem and must expose confidence / warning information.

These costs are accepted.

---

## 24. Acceptance Criteria

The Music Pack is considered implemented when all of the following hold:

1. `music.analyze` returns normalized BPM, key, scale, beat, and loudness data for reference fixtures.
2. `music.separate` produces artifact-backed stems with at least vocals/instrumental support.
3. `music.fingerprint` generates stable fingerprints and supports local recording comparison.
4. `music.transcribe_notes` returns normalized note events and a MIDI artifact.
5. `music.transcribe_multitrack` can run MuScriptor through an isolated provider and return instrument-attributed tracks.
6. ROSVOT can be installed independently and exposed as `music.transcribe_vocal` without affecting stable providers.
7. ACE-Step is physically isolated into the optional generation pack.
8. All provider outputs validate against shared Music schemas.
9. Failure of any experimental provider does not break stable Music capabilities.
10. `specialist doctor` reports Stable / Experimental / Heavy provider readiness separately.
11. No LLM-facing API requires knowledge of provider implementation names.
12. Real-world regression fixtures run in CI or the project's benchmark workflow.

---

## 25. Final Decision

**ACCEPT Music Intelligence Pack.**

Adopt:

```text
Essentia
audio-separator
Chromaprint
Basic Pitch
MuScriptor
ROSVOT
ACE-Step
```

with the following maturity boundaries:

```text
Stable:
  Essentia
  audio-separator
  Chromaprint
  Basic Pitch

Experimental:
  MuScriptor
  ROSVOT

Heavy Generative:
  ACE-Step

Watchlist:
  VocalParse
  YourMT3+
```

The stable public capability contract is:

```text
music.analyze
music.separate
music.fingerprint
music.transcribe_notes
music.transcribe_vocal
music.transcribe_multitrack
music.generate
```

The governing principle is:

> **Standardize the musical capability, not today's model.**

A future provider may replace MuScriptor, ROSVOT, Basic Pitch, or ACE-Step without requiring changes to applications or LLM tool contracts.
